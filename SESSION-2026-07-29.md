## Session 15 — ground-truth disasm, real vtable+0x40 fix, new kill() blocker (2026-07-29 ~17:55-18:30)

### New technique that unlocked everything
All prior guesses about `0x120370c0`'s "singleton/vtable" came from static file bytes or
pre-decryption dumps. This session instead dumped memory **from the live unidbg process, after
`JNI_OnLoad` runs** (self-decryption ctors have already run by then), printed the hex to the
harness log, and disassembled those *exact* bytes with capstone over SSH on `.40`. This gave
100%-accurate ground truth for the first time. Use this technique before hypothesizing about
any other address in this binary — manual byte-level guessing in this obfuscated code is a trap
(see the `obj(r0)` mistake below).

### Verified disasm — `0x120370ba`-`0x120370e0` (the vtable+0x40 check)
```
0x120370ba: ldr r0,[pc,#0x30]   ; literal
0x120370bc: add r0,pc           ; r0 = GOT slot 0x12082340 (resolved: pc+lit(0x4b280)=0x12082340)
0x120370be: ldr r0,[r0]         ; r0 = P1 = *(0x12082340)
0x120370c0: ldr r0,[r0]         ; r0 = P2 = *P1   <- the real "singleton"
0x120370c2: ldr r1,[r0,#0x40]   ; r1 = *(P2+0x40) <- the vtable slot (was NULL)
0x120370c4: mov r0,r5           ; r0 OVERWRITTEN with r5 (JavaVM*) right before the call
0x120370c6: blx r1
0x120370c8: ldr r0,[sp]
0x120370ca: bl #0x12037878      ; second check right after
```
**Trap avoided:** the very first diagnostic run read `r0` *at* the `blx` hook and saw
`0xfffe0080`, which looked like a TLS base or bogus sentinel. It's actually just `r5` (JavaVM*)
— `mov r0,r5` at `0x120370c4` overwrites `r0` right before the call. `P2` (the real vtable
object) is a completely different value (`0x120868f0`) never visible in `r0` at that point.

Harness already had `*0x12082340=sa(0x120868e0)`, `*sa=sb(0x120868f0)` (from the session-13/14
"singleton chain" fix) — so **P1=sa, P2=sb**. Session 14 called `sb` the "classname buffer" —
correct, ctors write a string there, which is exactly why `P2+0x40` was naturally NULL: it was
never meant to double as a vtable-having object without more of its fields populated too.

### Real fixes (not hacks) applied to `_scratch/Unpack.java`
1. `SCRATCH` page remapped `R|W|X` (was `R|W`); a genuine 4-byte Thumb stub
   (`movs r0,#1; bx lr` = bytes `01 20 70 47`) written at `SCRATCH+0x800`.
2. `P2+0x40` (`0x12086930`) = stub address `|1` (thumb bit), written **before** calling
   `JNI_OnLoad`. Verified: the `blx r1` hook now sees `origR1` already valid (no override
   needed) — the call executes for real, with a real return, not a PC-skip.
3. `P2+0x188` (`0x12086a78`) = non-zero (scratch ptr). Found via disasm of `0x12037a80`
   (`ldr r0,[r0,#0x188]; cmp r0,#0; beq→kill()`). Was 0 because CTOR-PATCH only ever wrote a
   *different* object's `+0x188` (at `0x120923c0`, unrelated to P2). Verified via trace hook:
   `cmp-r0-after-P2+0x188 (r0) = 0x7f000000` (non-zero, branch skipped).
4. `P2+0x109` (`0x120869f9`) = 0. Third guard, read inside the kill() block itself
   (`ldrb r0,[r0,#0x109]; cbz r0,→skip an extra SIGABRT(6) call`).

### New true blocker: unconditional `kill(pid, SIGKILL)` — confirmed non-patchable
Even with all 3 fields correct, execution still reaches `0x12037b80`'s `kill(pid,9)`. Traced the
full chain with trace-only hooks (gated on `jniPhase`, zero side effects):
```
0x12037a92-9c: r8 = *(0x12082340) = P1(sa)        ; same GOT chain, one less deref than P2
0x12037a9c-a0: r0 = *(*(r8)+0x188) = *(P2+0x188)  ; fix #3 -> non-zero -> branch to kill() skipped
0x12037aa8-ae: blx #0x1207b5a0 (already forced ret=1 by a session-13 hook) -> branch skipped
0x12037ab2-bc: real getpid() svc -> r4 = pid (e.g. 0x171f / 0x17b1 across runs)
0x12037abe-c2: r5 = literal 0xfffff000 (resolved via disasm); cmp r0(pid),r5; bls -> ALWAYS TAKEN
```
The `bls` target is **`0x12037b4a`, not `0x12037b40`** — skips the `movs r4,#0` reset, so **r4
keeps the real pid** through to the final `svc` (`kill(r4=realpid, r1=9)`). The `0xfffff000`
compare is not a real gate (any real pid is far smaller) — **every path that reaches
`0x12037a92` unconditionally ends in a real `kill(pid,9)`**, independent of the P2 fields.

**Direct experiment** (temporarily let the real `svc` execute instead of PC-skipping):
```
java.lang.UnsupportedOperationException: SIGKILL pid=5919 is fatal and does not return (emulated abort)
	at com.github.unidbg.linux.AndroidSyscallHandler.kill(AndroidSyscallHandler.java:712)
```
unidbg **deliberately** models `kill(_, SIGKILL)` as non-returning (matches real Linux: SIGKILL
can't be caught by the target). No register/memory patch after the `svc` can undo this. Reverted
the experiment; harness is back on the session-13 soft-ret + forced-`JNI_VERSION_1_6` fallback
(works, but is still a forced, not natural, completion — `RegisterNatives` still doesn't fire).

### Do NOT (additions)

- Don't confuse `obj(r0)` at the `0x120370c6` `blx` hook with the vtable object — it's `r5`

## Session 15d — `0x1201e378` fully cleared, new object needed for `0x12037c18` (2026-07-29 ~19:20-19:40)

### Isolated the `0x1201e378` crash precisely
Added register-dump hooks at each link of the chain instead of guessing:
```
r6(GOT_Y) = 0x120868e0 (=sa)         ; same GOT chain as our known P1/P2
*(GOT_Y)  = 0x120868f0 (=P2)         ; confirmed - this really is our own singleton
before ldr r5,[r0,#0x40]: r0=0x120868f0(P2)   ; wait — this is AFTER the fix (see below)
```
Actual bug: `0x1201e398: ldr r0,[r0,#0x10]` — **`P2+0x10`** (`0x12086900`), a slot we'd never
touched, held garbage `0x412f6d70`. Next instruction `ldr r5,[r0,#0x40]` computed
`0x412f6d70+0x40=0x412f6db0` → unmapped → crash. **Fix:** `mem_write(P2+0x10, P2)` — point it
at itself. `P2+0x40` is already our real stub, so this reuses working infra instead of building
a whole new object. Verified: chain now resolves `r0=0x120868f0`, `*(r0+0x40)=0x7f000801`
(our stub), `blx r5` succeeds, `VTABLE_STUB entry reached`, returns `r0=1`.

### Full disasm of `0x1201e378` (0x180 bytes) — same pattern repeated 5 more times
Not just `+0x40` — this function calls through `P2` (always re-derived as `*(*(r6))` `->
[+0x10]` `-> P2` thanks to the self-ref) at offsets `+0x60`, `+0x5c` (5 separate call sites — a
`DeleteLocalRef`-style conditional cleanup pattern near the function's tail), `+0x18`, `+0x68`,
`+0x35c`. Every call site does `cmp r0,#0`/`cbz r0` → branch to a shared failure/cleanup label
(`0x1201e4be`) if the call returns 0. Since our stub always returns `1`, populating **all** of
these offsets with the same `VTABLE_STUB` pointer satisfies every check.

**Fix applied:** loop writing `VTABLE_STUB|1` into `P2+0x60`, `P2+0x5c`, `P2+0x18`, `P2+0x68`,
`P2+0x35c` (plus the existing `P2+0x10` self-ref and `P2+0x40` stub). **Verified via the wide
walk trace:** `0x1201e378` now runs to completion and returns — `[walk] 0x120378a4` (the
instruction immediately after `bl 0x1201e378` in the caller) appears, something no prior run
ever reached. Zero exceptions from this function anymore.

### New blocker: `bl 0x12037c18` needs a second, separate fake object
Immediately after `0x1201e378` returns, the caller does `mov r0,r4; bl 0x12037c18` — this
crashes almost instantly with a fresh `FETCH_PROT`. Partial disasm (only the first 0x40 bytes
dumped, from an earlier round) shows a **different** object entirely:
```
0x12037c32: ldr r0,[pc,#0x3a0]; add r0,pc; ldr.w sb,[r0]   ; sb(r9) = *(new GOT slot)
0x12037c3a: ldr.w r0,[sb]                                   ; r0 = *(new_obj)
0x12037c3e: ldr r1,[r0,#0x24]                                ; r1 = *(new_obj+0x24)
0x12037c40: ldr r0,[r0,#0x44]                                ; r0 = *(new_obj+0x44) - call arg
0x12037c42: ldr r4,[r1,#0x38]                                ; r4 = *(r1+0x38) - function ptr
0x12037c4c: blx r4
```
This does **not** go through our `r6`/`0x12082340`/`P2` chain at all — it's a fresh GOT slot
feeding `sb`, and needs a TWO-level object chain (`new_obj+0x24` → another object → `+0x38`)
rather than the flat one-object-many-offsets shape `P2` has been serving as. The literal pool
address for the new GOT slot (`ldr r0,[pc,#0x3a8]` at `0x12037c24`) falls outside the 0x40 bytes
already dumped — needs a wider dump (same technique, just a bigger byte count) to resolve.

## Session 17 — decrypt-loop cleared, REAL FindClass reached for the first time (2026-07-29 ~20:55-21:20)

### Fix #1: bound the decrypt loop
Added a `CodeHook` at `0x12037db0` (the instruction right after `asr.w sl,r6,#4` at `0x12037dac`)

### Fix #2: the trailing call, and a mistake worth documenting
Disasm showed a second call to the same decrypt routine right after the loop:
`0x12037dc8: add r2,sp,#0x128; mov r0,r4; mov r1,r5; bl 0x1203a314`. `r5` is the "remaining
bytes" countdown that was decremented every loop iteration but never reset — with the loop
artificially truncated at 6, `r5` is still a huge leftover value, so this trailing call also

**First attempt:** forced `r5=0` at `0x12037dcc` (right before `mov r1,r5` copies it into `r1`).

actually helping — turned out `r5` gets reused right after, at `0x12037e0a` (`mov r0,r5`), as an

had kept its real value.

**Correct fix:** hook `0x12037dce` (the `bl 0x1203a314` instruction itself, AFTER `mov r1,r5` at
`0x12037dcc` already ran) and zero only `r1` there. `r5` itself is left completely untouched,
preserving it for the later legitimate use. Re-ran with this surgical fix — **identical
downstream behavior actually** (same crash, same registers) as the r5=0 attempt, which at first
looked like it disproved the r5-reuse theory... but see below, the real bug was never r5 at all.

`0x1207b6f0`/`0x1207b700` are real `strcspn`-shaped helpers. **The function is a text tokenizer**

### The actual bug: binary data fed to a text function
Our call passes `r0 = 0x12240484` — the raw XOR-decrypted entries buffer (confirmed via session
16's own dump: first 4 bytes are `0x00 0x00 0x00 0x00`). Treated as a C string, `strcspn` on an
empty string (first byte NUL) returns `0`, `haystack[0]` IS the NUL byte, and the function fails
on its very first real check - **deterministically, independent of any register-level count/
pointer patch upstream.** This is qualitatively different from every prior blocker this project
(`P2+0x40`, `P2+0x24`, `FLAG_X`, the decrypt-loop count, etc.) — those were all "some slot holds
garbage, write a plausible value into it, downstream code just checks non-zero/non-null." This
one needs the ACTUAL CONTENT to be a real, sensible null-terminated string (a class name, a
method signature) — no amount of "write 2 here, write a stub pointer there" changes what's
fundamentally binary data into text.

### Why this matters for strategy going forward
The "cheap-fix-first, populate-the-slot-and-move-on" methodology that cracked every blocker so
far has reached its natural limit here. Getting genuinely correct string data flowing requires
either finding an upstream step that legitimately produces real text (most likely: the entry
XOR-decrypt using its TRUE key/count instead of our hand-forced approximations — if the real
key/count are right, the decrypted bytes might BE readable text, e.g. a class name string packed
into the entries), or tracing back to `0x12037c18`'s own caller to understand what `r0` is
supposed to represent in the first place (never established — this whole investigation started
mid-function without confirming the caller's intent).

### Key findings
- **Scan architecture** (from subagent analysis): Veneer table at 0x1207b400 has 16-byte ARM entries that load targets from pointer table at 0x12082408+ and branch. Scan walks linker data segment looking for soinfo structures. Pointer table at 0x12082340 has stale on-disk entries (0x7b290) never populated by ctors.
- **Scan exit**: CBZ at 0x12037664 → exit at 0x12037692 when R0=0 after BLX. Verified: R0=0 in LastResortHook triggers exit.
- **BL at 0x1203767c**: This is the scan-call instruction (→0x1207b7d0). LR from all FETCH events = 0x12037681. Scan-kill hook at this address bypasses the page walk.
- **IOResolver never triggers**: N.l doesn't read the APK via `open()` syscalls — probably uses JNI asset APIs (AAssetManager) which bypass the IOResolver.

### What doesn't work
