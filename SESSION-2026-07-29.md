## Session 15 — ground-truth disasm, real vtable+0x40 fix, new kill() blocker (2026-07-29 ~17:55-18:30)

### New technique that unlocked everything
All prior guesses about `0x120370c0`'s "singleton/vtable" came from static file bytes or
pre-decryption dumps. This session instead dumped memory **from the live unidbg process, after
`JNI_OnLoad` runs** (self-decryption ctors have already run by then), printed the hex to the
harness log, and disassembled those *exact* bytes with capstone over SSH on `.40`. This gave
100%-accurate ground truth for the first time. Use this technique before hypothesizing about
any other address in this binary — manual byte-level guessing in this obfuscated code is a trap
(see the `obj(r0)` mistake below).

### Verified disasm — `0x120370ba`-`0x120370e0` (the vtable+0x40 check)
```
0x120370ba: ldr r0,[pc,#0x30]   ; literal
0x120370bc: add r0,pc           ; r0 = GOT slot 0x12082340 (resolved: pc+lit(0x4b280)=0x12082340)
0x120370be: ldr r0,[r0]         ; r0 = P1 = *(0x12082340)
0x120370c0: ldr r0,[r0]         ; r0 = P2 = *P1   <- the real "singleton"
0x120370c2: ldr r1,[r0,#0x40]   ; r1 = *(P2+0x40) <- the vtable slot (was NULL)
0x120370c4: mov r0,r5           ; r0 OVERWRITTEN with r5 (JavaVM*) right before the call
0x120370c6: blx r1
0x120370c8: ldr r0,[sp]
0x120370ca: bl #0x12037878      ; second check right after
```
**Trap avoided:** the very first diagnostic run read `r0` *at* the `blx` hook and saw
`0xfffe0080`, which looked like a TLS base or bogus sentinel. It's actually just `r5` (JavaVM*)
— `mov r0,r5` at `0x120370c4` overwrites `r0` right before the call. `P2` (the real vtable
object) is a completely different value (`0x120868f0`) never visible in `r0` at that point.

Harness already had `*0x12082340=sa(0x120868e0)`, `*sa=sb(0x120868f0)` (from the session-13/14
"singleton chain" fix) — so **P1=sa, P2=sb**. Session 14 called `sb` the "classname buffer" —
correct, ctors write a string there, which is exactly why `P2+0x40` was naturally NULL: it was
never meant to double as a vtable-having object without more of its fields populated too.

### Real fixes (not hacks) applied to `_scratch/Unpack.java`
1. `SCRATCH` page remapped `R|W|X` (was `R|W`); a genuine 4-byte Thumb stub
   (`movs r0,#1; bx lr` = bytes `01 20 70 47`) written at `SCRATCH+0x800`.
2. `P2+0x40` (`0x12086930`) = stub address `|1` (thumb bit), written **before** calling
   `JNI_OnLoad`. Verified: the `blx r1` hook now sees `origR1` already valid (no override
   needed) — the call executes for real, with a real return, not a PC-skip.
3. `P2+0x188` (`0x12086a78`) = non-zero (scratch ptr). Found via disasm of `0x12037a80`
   (`ldr r0,[r0,#0x188]; cmp r0,#0; beq→kill()`). Was 0 because CTOR-PATCH only ever wrote a
   *different* object's `+0x188` (at `0x120923c0`, unrelated to P2). Verified via trace hook:
   `cmp-r0-after-P2+0x188 (r0) = 0x7f000000` (non-zero, branch skipped).
4. `P2+0x109` (`0x120869f9`) = 0. Third guard, read inside the kill() block itself
   (`ldrb r0,[r0,#0x109]; cbz r0,→skip an extra SIGABRT(6) call`).

### New true blocker: unconditional `kill(pid, SIGKILL)` — confirmed non-patchable
Even with all 3 fields correct, execution still reaches `0x12037b80`'s `kill(pid,9)`. Traced the
full chain with trace-only hooks (gated on `jniPhase`, zero side effects):
```
0x12037a92-9c: r8 = *(0x12082340) = P1(sa)        ; same GOT chain, one less deref than P2
0x12037a9c-a0: r0 = *(*(r8)+0x188) = *(P2+0x188)  ; fix #3 -> non-zero -> branch to kill() skipped
0x12037aa8-ae: blx #0x1207b5a0 (already forced ret=1 by a session-13 hook) -> branch skipped
0x12037ab2-bc: real getpid() svc -> r4 = pid (e.g. 0x171f / 0x17b1 across runs)
0x12037abe-c2: r5 = literal 0xfffff000 (resolved via disasm); cmp r0(pid),r5; bls -> ALWAYS TAKEN
```
The `bls` target is **`0x12037b4a`, not `0x12037b40`** — skips the `movs r4,#0` reset, so **r4
keeps the real pid** through to the final `svc` (`kill(r4=realpid, r1=9)`). The `0xfffff000`
compare is not a real gate (any real pid is far smaller) — **every path that reaches
`0x12037a92` unconditionally ends in a real `kill(pid,9)`**, independent of the P2 fields.

**Direct experiment** (temporarily let the real `svc` execute instead of PC-skipping):
```
java.lang.UnsupportedOperationException: SIGKILL pid=5919 is fatal and does not return (emulated abort)
	at com.github.unidbg.linux.AndroidSyscallHandler.kill(AndroidSyscallHandler.java:712)
```
unidbg **deliberately** models `kill(_, SIGKILL)` as non-returning (matches real Linux: SIGKILL
can't be caught by the target). No register/memory patch after the `svc` can undo this. Reverted
the experiment; harness is back on the session-13 soft-ret + forced-`JNI_VERSION_1_6` fallback
(works, but is still a forced, not natural, completion — `RegisterNatives` still doesn't fire).

### Do NOT (additions)
- Don't try to "fix" the `getpid()`-vs-`0xfffff000` compare — always true, not a real gate.
- Don't let the real `svc #0` execute at `0x12037b5e`/`0x12037b88` — unidbg throws, confirmed.
- Don't confuse `obj(r0)` at the `0x120370c6` `blx` hook with the vtable object — it's `r5`
  (JavaVM*). The real object is `P2 = *(*(0x12082340))`.
